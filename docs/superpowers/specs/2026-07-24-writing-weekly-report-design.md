# writing-weekly-report 设计

**日期:** 2026-07-24  
**状态:** 已批准（对话确认）  
**仓库:** `xue7106211/allen-skills`  
**Skill 目录:** `writing-weekly-report/`

## 背景与目标

用户需要一份可复用的 Agent Skill，把本周已完成工作整理成固定风格的 Markdown 周报。风格以用户既有周报样本为准：按项目分桶、`1.` / `1.1.` 层级、强动词开头、技术术语精确、带证据链接、结果导向。

本 Skill 编码的是**整理与成稿流程**，不是某一次周报的叙事。

## 范围

### 纳入

- 多源素材采集：用户口述/粘贴、Git commits / PR / MR、飞书文档 / Wiki / 相关记录
- 仅输出「本周完成」板块
- 默认交付 Markdown；飞书写入/发群为可选，且必须先征得用户同意
- 按 writing-skills（TDD for skills）先基线失败再写 skill，再验证通过
- 落盘在 `allen-skills` monorepo；完成后用 Skills CLI 同步到个人 skills

### 不纳入

- 「下周计划」「风险/阻塞」等额外板块
- 自动、默认发飞书（无确认门闩则禁止）
- 编造未提供的成果、数据或链接
- 配套自动化脚本 / CLI（首版不做方案 C）
- 跨人周报模板或多团队格式变体

## 决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 架构 | 方案 B：流程型 Skill（采集 → 归类 → 按习惯成稿） | 覆盖多源输入，输出形状稳定；比纯模板更可执行，比重脚本更轻 |
| 输出 | 默认 Markdown；飞书需二次确认 | 符合「先可读、再分发」习惯 |
| 板块 | 只要本周完成 | 对齐用户样本 |
| 存放 | `allen-skills/writing-weekly-report/`，再 `npx skills add` 到个人 | 与 monorepo 安装模型一致 |
| Skill 名 | `writing-weekly-report` | 动名词命名，便于发现 |

## 触发条件

Skill `description` **只写何时用**，不总结流程（避免 agent 只读 description 走捷径）。

触发语境包括但不限于：

- 「写周报」「本周周报」「整理本周工作」「weekly report」
- 用户粘贴一堆事项并要求按周报格式输出
- 用户提供 Git / 飞书材料并要求汇总成周报

## 核心流程

```text
确定周期 → 采集素材 → 抽取事实 → 按项目归类 → 按表达习惯成稿 → 自检 → 交付 Markdown
                                                              ↓
                                                    仅在用户明确同意后发飞书
```

### 1. 确定周期

- 用户未指定：默认「本周一至今天」（本地时区）
- 用户指定了日期范围或「上周」等：按用户说明

### 2. 采集素材

按用户**实际给出的来源**组合使用，缺什么就缺什么，不假装采过：

| 来源 | 典型输入 | Agent 行为 |
|---|---|---|
| 用户笔记 | 口述、粘贴列表、聊天摘要 | 直接作为主事实源 |
| Git | 仓库路径、分支、PR/MR 链接或要求「看 commits」 | 在周期内读取 commits / PR / MR 标题与描述 |
| 飞书 | 文档/Wiki 链接或明确「去飞书找」 | 用已配置的飞书能力拉取；不可用则说明并请用户粘贴 |

素材冲突时：以用户明确陈述为准，Git/飞书作证据与补充。

### 3. 抽取事实

每条事实必须包含动作、对象、结果或原因；证据有则必附，无则省略且不编造：

1. **动作**（可落到强动词）
2. **对象**（系统、组件、文档、流程）
3. **结果或原因**（做完了什么、为何这样改）
4. **证据**（URL、MR、Wiki；没有则省略，不编造）

过滤：进行中、计划中、纯会议出勤且无产出的条目，默认不进「本周完成」，除非用户明确要求保留。

### 4. 按项目归类

- 一级桶 = 项目或主题名（如 HyperOS Design System、OS4 UI Kit）
- 同一项目下多条成果用 `1.1.` `1.2.` …
- 无法归类的零散项：合并进最接近的桶；仍不行则单独一桶，命名具体，禁止「其他杂项」式空桶名（可用具体主题，如「设计规范探索」）

### 5. 按表达习惯成稿

输出形状：

```markdown
1. {项目名}
1.1. {强动词}{对象}{结果/原因}{可选链接}
1.2. ...
2. {项目名}
2.1. ...
```

表达规则：

- 中文叙述 + 必要英文术语（MVP、SEO、favicon、OG、UI Kit、Bug、block 等）
- 条目以强动词开头：构建 / 申请 / 落地 / 优化 / 输出 / 支持 / 补充 …
- 有权威链接则附上
- 结果导向：写清「改了什么 → 为了什么」
- 简洁、技术、可执行语气；禁止散文开场、总结段、表情符号堆砌

### 6. 自检清单

成稿前检查：

- [ ] 只有「本周完成」，无下周计划 / 风险专节
- [ ] `1.` / `1.1.` 层级正确
- [ ] 每条以强动词开头
- [ ] 无编造链接或未发生成果
- [ ] 进行中未伪装成已完成

### 7. 交付与飞书门闩

1. 先输出完整 Markdown 周报
2. 询问是否写入飞书文档或发到群/私聊
3. **仅在用户明确同意后**执行飞书操作；未同意则结束

## 文件结构

```text
writing-weekly-report/
  SKILL.md
  examples/
    sample-weekly-report.md
```

- `SKILL.md`：触发说明、流程、表达契约、常见错误、飞书门闩
- `examples/sample-weekly-report.md`：基于用户样本的黄金示例（可脱敏内部链接说明）

根 `README.md` 的 Skills 表增加一行；安装说明补充该 skill 名。

## Skill 正文约束（写作时）

遵循 writing-skills / agentskills 规范：

- YAML：`name`、`description`；`description` 以 `Use when...` 开头，第三人称，**不总结流程**
- 编码流程，而非只描述「好周报长什么样」
- 严格措辞，避免「尽量」「适当」等不可执行词
- 表达类失败用**正向契约**（输出必须长什么样），纪律类失败（擅自发飞书）用禁止 + 门闩
- 控制篇幅；细节放 example，不堆多语言示例

## 测试计划（RED → GREEN → REFACTOR）

### 基线失败（无 skill）

压力场景示例：

1. 用户给一坨无结构笔记 +「快点写周报」→ 易变成散文或 bullet 散文
2. 同时给 Git log → 易逐条罗列 commit message，不按项目归类
3. 提到飞书 → 易未经确认就调用发送
4. 素材含「下周要做」→ 易自动加「下周计划」节

记录真实偏离，再写 skill 对症下药。

### 通过标准（有 skill）

- 输出符合表达契约与自检清单
- 未同意时零飞书写入/发送
- 多源输入时按项目归类，而非按来源分节

## 同步到个人 skills

Skill 合入 monorepo 并（如需）推送远程后：

```bash
npx skills add xue7106211/allen-skills --skill writing-weekly-report
```

验收：个人 skills 目录可被 Agent 发现；用「写周报」类话术能加载本 skill。

## 验收标准

- 存在 `writing-weekly-report/SKILL.md` + 黄金示例
- 根 README 列出该 skill
- RED/GREEN 测试记录表明关键偏离已被纠正
- 可通过 Skills CLI 安装到个人环境
- 任意一次「写周报」运行：默认只出 Markdown；飞书仅在确认后发生

## 明确不做（再强调）

- 不默认发飞书
- 不写下周计划 / 风险专节（除非用户日后改 scope）
- 首版不写采集脚本
