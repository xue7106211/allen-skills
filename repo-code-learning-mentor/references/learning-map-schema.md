# 学习地图与主题卡规范

在新仓库的导航状态中读取本文件。根据真实源码生成地图；不要把以下分类当成必须存在的功能清单。

## 主题分类

| 编号 | 镜头 | 只在发现对应证据时创建主题 |
| --- | --- | --- |
| D | 设计实现 | 设计 token、主题、组件 API、组件变体、CSS/样式架构、布局、响应式、动效、可访问性。 |
| F | 前端运行原理 | 入口与模块、渲染、事件、状态、表单、路由、数据请求、异步、TypeScript、错误处理。 |
| E | 工程化质量与交付 | 包管理、构建、环境变量、lint/格式化、类型检查、测试、性能、CI/CD、监控。 |

按组使用连续编号，例如 `D1`、`D2`、`F1`、`E1`。一个主题可以关联多种镜头，但只用其最适合的主编号，并在卡片中标注关联镜头。

## 主题卡格式

每张卡最多 6 行，使用下面的结构：

```markdown
### D1 · 主题名称
- 证据：`实际文件路径`（必要时附行号）
- 学什么：本项目中要读懂的代码与界面能力
- 三个镜头：设计实现 / 前端原理 / 工程化中的相关项
- 前置与难度：前置知识；入门、进阶或挑战
- 推荐原因：与产品体验、设计工程师能力或后续主题的具体关系
```

主题应按学习依赖和产品影响排序；优先保留 6–12 张最有学习价值的卡。源码庞大时按区域或功能聚合，不把每个文件都做成卡。

## 项目图谱与路线

项目图谱应说明实际存在的连接，例如：路由/页面 → 组件 → 样式或 token、用户事件 → 状态 → 数据/API、源码 → 测试 → 构建。没有可靠关系时使用“待确认”，而非箭头猜测。

根据发现的主题提供三条短路线：

1. **设计落地**：优先串联 token、组件、布局、响应式或可访问性主题。
2. **交互与前端逻辑**：优先串联入口、事件/状态、路由、数据和类型主题。
3. **质量与交付**：优先串联本项目的类型检查、测试、构建、性能或部署主题。

每条路线最多列出 3–5 张实际主题卡，并标明与另两条路线相交的主题。缺少该类证据时写“未发现相应源码”，再推荐一张能补足该能力的已发现主题；不要发明主题。

## 选择与深入

用户输入编号、主题名、文件路径或“推荐路线”时，先解析到一张主题卡。若命中多个主题，简短列出候选卡请用户选一个；若无匹配，回到地图并建议最接近的已发现主题。

一个主题可以分为多个小节。每节只聚焦一个连续逻辑块，并始终输出：项目内代码证据、概念对照、语法说明、可迁移概念和下一学习动作。仅当代码与 Figma 存在真实对应时才使用 Figma；否则用更准确的非 Figma 类比，并说明类比边界。用户完成或切换主题后，更新对话内进度即可；不要在仓库写入学习记录，除非用户明确要求。
