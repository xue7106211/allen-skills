# Allen Writing Skill

把 Skill 视为 Agent 的工作流接口：它定义何时介入、读取什么、如何推进，以及如何验证自身确实改变了行为。目标是产出**小而完整、可预测、可维护**的 Skill，而不是把通用建议堆成一份长提示词。

## 适用边界

- **使用：** 新建 Skill、重写或审查现有 Skill、把重复的人类操作沉淀为 Agent 工作流。
- **不使用：** 只安装、列出或启用现成 Skill；普通的一次性提示词；任务本身还没有稳定的工作流时。
- 用户指定名称、位置、调用方式、工具范围或交付形态时，以其为准。不要因为写了 Skill 就扩大真实任务的授权范围。

## 先形成最小设计

在写任何文件前，用一小段设计说明回答：

1. **任务承诺：** 该 Skill 在什么输入下，帮助用户稳定完成什么结果？它明确不处理什么？
2. **触发策略：** 选择模型可调用、仅用户显式调用，或保留现有策略；说明选择的原因。
3. **主路径与分支：** 写出共同的步骤、需要额外信息或模板的分支，以及人类确认点。
4. **成功证据：** 任务完成后可检查的产物、行为或不变量是什么？

若无法说清任务承诺或成功证据，先向用户索要一个真实用例或范围说明；不要用泛泛规则填满空白。

## 设计触发：方便与确定性的取舍

- **模型可调用**适合任务意图明显、遗漏会造成实际损失、且描述足以让模型可靠判断的场景。描述必须写清“做什么、何时做、何时不做”。
- **仅用户调用**适合高成本、容易误触发、需要使用者明确选择策略，或模型是否调用会带来不可接受不确定性的场景。
- 模型可调用会增加常驻描述和选择负担；仅用户调用会增加用户记忆与编排负担。两者没有默认赢家。
- 除非用户明确要求显式调用，保留自动发现；不要因担心副作用而隐藏 Skill，真实的外部写入、发送或破坏性动作应在执行前单独确认。

## 编排结构：步骤与参考分开

将每项内容归入唯一角色：

- **步骤：** 所有适用路径都需要的行动、判断和停止条件。
- **参考：** 完成特定步骤所需的模板、格式、领域规则、数据结构或示例。

`SKILL.md` 只保留目的、分流、共同步骤、关键约束和对参考资料的链接。仅某个分支使用的模板或长规则，应放进 `references/`，并明确写出“何时读取它”。不要把未来分支的资料预加载进主文件。

不为形式而创建目录、脚本、样例或 README。只有重复执行且需要确定性时才加脚本；只有确实按需读取时才加参考资料。每条规则、模板和格式要求都应有一个唯一权威来源。

## 写出能引导行为的指令

1. 用动词和可观察结果写步骤，例如“检查候选范围并报告未确认项”，不要只写“仔细分析”。
2. 为关键策略选择一个简短、已有明确语义的**引导词**，并在相关步骤中一致使用。例如，端到端增量交付可统一称为“垂直切片”。不要为普通常识发明术语。
3. 如果 Agent 总是草率完成某一步，先把该步的产物和完成标准写具体；仍不足时，将它拆成独立阶段或独立 Skill，使当前阶段不被后续目标分散注意。
4. 区分事实、合理推断和待确认项；缺少证据时停止扩展，而非编造流程、工具或项目约定。
5. 对有风险的操作给出适度停止条件。安全边界应针对真实风险，而不是把每个普通动作都变成审批流程。

## 精简与审查

完成草案或审查现有 Skill 时，读取 [Skill 审查清单](references/skill-review-checklist.md)，逐项检查。

**删除测试是验证放行门，而非可选建议。** 用户只要说“验证”“检查”或“审查”一个 Skill，即默认同时要求静态检查、前测和适用的删除测试；不要等待用户额外点名删除测试。未完成三者前，不得声称该 Skill 已“验证通过”或“可稳定使用”；只能如实报告已完成的层级与缺失项。

重点执行三项删减：

- **去重：** 合并重复要求，保留一个权威位置。
- **清沉积：** 移走只属于局部分支的内容；删除过期、无关或无人维护的段落。
- **删除测试：** 暂时移除某条规则并判断预期行为、产物或安全性是否会变差；若不会，这条规则多半是空操作，应删除或改写得更具体。

不要为了“完整”重复系统已有的通用能力、政策或工具说明；只保留会改变此类任务决策的知识。

## 落地与验证

1. 以 `kebab-case` 创建以 Skill 命名的目录，写入含 `name` 与区分性 `description` 的 `SKILL.md`。
2. 仅在界面发现、默认提示或调用策略确有价值时，添加 `agents/openai.yaml`；其展示名、短描述和默认提示必须与实际能力一致。
3. 若运行环境提供 Skill 验证器，运行它；无验证器时至少检查 YAML frontmatter、内部相对链接、文件命名、未完成占位符与变更 diff。
4. 使用一个贴近真实的请求进行前测：确认会命中该 Skill、能选择正确分支、只读取相关参考，并产出已定义的成功证据。不要用“是否复述了 Skill 文案”当测试。
5. 在隔离的临时副本中，按 [删除测试协议](references/skill-review-checklist.md#删除测试协议必须执行) 移除高杠杆候选规则，并用同一场景与基线对照。根据可观察差异决定保留、改写或删除；不要用主观推演替代此测试。
6. 修改已有 Skill 时保留用户已有的资源和配置；进行最小改动，不顺带重写无关内容。

## 交付

交付时简要说明：Skill 的定位与触发方式、创建或更新的文件、已验证的结果，以及尚未执行的外部操作。除非用户要求，不自动安装、提交、推送或发布。
